## 결정: 7-2(Supabase 연결)는 하지 않는다 (2026-11-07)

- **결정**: 커뮤니티를 서버(Supabase)에 연결하는 7-2단계를 진행하지 않는다. 커뮤니티는 브라우저 저장(IndexedDB)으로 남는다.
- **이유**: 이 앱은 공식 배포용이 아니라 **기능 구성을 보여 주는 시연용**이다. 시연에는 한 브라우저 안에서 글쓰기·작성 제한·신고·선수 카드 연동이 동작하는 것으로 충분하고, 서버·로그인·저장 비용·운영 정책(PRD 미확인 항목)을 갖출 필요가 없다.
- **남겨 둔 것**: 저장소 인터페이스(`data/source.ts`의 `CommunityRepository`, `storage: 'shared'` 포함)와 서버에서도 쓸 수 있게 만든 작성 제한·글 규칙(`domain/community/`)은 그대로 둔다. 나중에 서버를 붙이게 되면 7절의 7-2 계획을 출발점으로 쓴다.
- **대신 한 일 (시연 준비)**: 처음 열어도 커뮤니티가 비어 보이지 않게 "데모 게시글" 예시 글을 넣고, 커뮤니티 화면에 "시연용이라 글이 이 브라우저에만 저장돼요" 안내를 넣었다 (4절 23·24번).

## 1. 실행

```bash
npm install
npm run dev        # 개발 서버
npm run check      # 타입 검사 + lint + 테스트
npm run build
npm run golden     # 데모 HTML에서 골든 데이터 다시 추출 (fixtures/demo-golden.json)
```

도구: Vite 8, React 19, TypeScript 6, React Router 8, Vitest 5(+ jsdom, Testing Library), oxlint.

## 2. 구조와 규칙

```
src/
├─ data/     ① 불러오기 — 리그를 아는 유일한 층 (demo/, mlb/, community/, 나중에 kbo/)
├─ domain/   ② 계산·규칙 — 리그를 모르는 순수 함수 (metrics/, games/, community/, 카탈로그, 백분위, 비교 …)
└─ ui/       ③ 화면 — 기능별 폴더 player · compare · games · community, 공통은 shared
```

- **층 경계** (`.oxlintrc.json`, `no-restricted-imports`로 강제)
  - data → domain·ui·react import 금지
  - domain → `data/types`만 import 가능 (domain 테스트 파일은 데이터 출처 import 허용)
  - ui → 리그 어댑터(`data/demo`·`mlb`·`kbo`·`community`) 직접 import 금지, `data/registry`를 거친다
- **값 없음 규칙**: 해당 없거나 모르는 값은 언제나 `null`. 원시 데이터 타입에 선택 필드(`?`)를 두지 않는다. domain의 리그 평균·백분위·비교는 `null`·`undefined`·`NaN`을 모두 값 없음으로 보고 분자·분모에서 뺀다 (`domain/missing.ts`).
- **데이터 출처 계약** (`data/source.ts`, `data/types.ts`)
  - `load()` → 원시 기록 + 리그 상수 + `meta`(시즌 표기, 계산 기준 문구, 반영일, 출처, 안내 문구, `available`)
  - `meta.available`: 기록 필드 하나하나의 있음/없음. 없다고 한 필드는 모든 선수에게 null이어야 한다 (`unavailableButPresent`로 검사). domain의 `metricAvailable`이 지표 → 원시 필드를 연결하고, 화면은 없는 지표 줄을 숨기고 보여 줄 것이 없는 탭을 닫는다.
  - `loadBattedBalls(id)`, 선택 함수 `loadWeek(weekId, ids)`(없으면 세이버 픽 챌린지를 닫는다)
  - 단위는 km/h · m/s · 0~1 비율로 바꿔서 넘긴다.
- **커뮤니티 저장소 계약** (`data/source.ts`의 `CommunityRepository`): 글 목록·구독·쓰기(파일 포함)·좋아요·신고·삭제·파일 주소. `storage`는 browser(이 브라우저에만)·memory(새로고침하면 사라짐)·shared(서버). ui는 `data/registry`의 `openCommunityRepository`로 연다. 작성 제한 검사·가림·자동 태그는 저장소에 넘기기 전에 domain(`domain/community/`)이 한다.
- **골든 테스트**: 데모 HTML을 jsdom에서 실행해 뽑은 값(`fixtures/demo-golden.json`)과 새 계산을 대조한다. 데모와 일부러 달라진 곳은 `demoQuirks`에 기록하고 테스트에서 예외로 처리한다.
- **CSS**: 색상·글꼴은 `ui/shared/tokens.css`에만 둔다. 나머지는 `base.css`·`metric.css`(공통)와 기능별 CSS.

## 4. 데모와 일부러 달라진 결정

데이터·계산
1. **지명타자 수비 항목**은 17개 모두 명시적으로 null (데모는 일부만 null, 나머지는 아예 없음). 테스트: `data/demo/demo.test.ts`
2. **DRS·OAA의 -0**을 0으로 정규화 (데모의 `Math.round`가 -0을 냄)
3. **리그 평균·백분위에서 값 없음 제외**: 데모의 리그 평균 수비율 NaN, 지명타자가 분모에 섞여 낮게 나오던 수비율 백분위를 고침. 골든 테스트에서 `fpct` 백분위만 예외. 테스트: `domain/percentile.test.ts`
4. **`regular`(주전) 플래그 제거**: 리그 상수 `qualifiedPA`(300타석)로 판단. 투수는 규정 이닝 기준이 아직 없어 데모처럼 전원을 비교 대상으로 둔다.
5. **0 표시 규칙**: 반올림한 결과가 0이면 부호 없이 표시("-0.0"·"+0.0" → "0.0"). 데모의 15건은 `demoQuirks.signedZeroFmt`. 테스트: `domain/compare.test.ts`, `domain/league.test.ts`
6. **지표별 있음/없음**: 출처에 없는 지표 줄은 숨기고(예: MLB의 DRS), 비교 화면에서도 뺀다. 탭은 안에 있는 지표가 하나라도 있으면 연다.

화면
7. **주소 기반 화면**: `/player/:id`, `/compare?a=&b=`, `/games/:game`. 상단 메뉴는 버튼 대신 링크(CSS `nav button` → `nav a`)
8. **CSS 추가 규칙 3개**: 닫힌 탭 흐리게, 키보드로 고른 자동완성 항목 강조, 메뉴 링크. 규칙 안에 직접 쓰던 색(#fff, 그림자, 오버레이, 백분위 막대 색)을 토큰으로 옮김. 백분위 막대 색은 `color-mix`로 같은 선형 보간
9. **자동완성 키보드 조작**(↑↓ Enter Esc), 검색 결과 없음 안내의 "위의 많이 찾은 선수" → "아래의"
10. **수비·트래킹 탭 아래 "데이터 출처 · 반영일"** (PRD 화면 5). 수비 탭 설명 문구는 실제로 보이는 지표만 나열

미니게임
11. **블라인드 퀴즈**: 한국 날짜 시드로 하루 1문제 모두 같은 문제(PRD), 푼 뒤 연습 문제. 보기 섞기는 고른 섞기(Fisher–Yates)로 바꿈
12. **세이버 픽 챌린지**: 주차(ISO, 한국 시간, 월요일 시작) 시드로 같은 문제. 주간 기록은 출처의 `loadWeek`로 받고, demo는 주차·선수별 시드로 시뮬레이션(데모는 매번 `Math.random`). 순위표는 "가상 참가자, 데모"로 표시. 채점 기준 문구는 `meta.basisLabel`
13. **이 타구, 안타일까?**: 수비수는 **그 팀에서 그 포지션 수비 이닝이 가장 많은 선수**(300타석 기준 아님, 동률은 목록에서 먼저 나온 선수, 없으면 수비 보정 없음). 출처에 없는 기록(스프린트 스피드, OAA, DRS, 능력치)은 보정·표시에 쓰지 않는다. 출처가 타구 데이터를 줄 때만 연다.
14. **지표 업다운**: 출처에 있는 지표만 문제로 낸다.
15. **게임 화면은 연 시각으로 날짜·주차를 고정**한다 (렌더링 중 자정을 넘겨도 문제가 바뀌지 않게).

커뮤니티 (7-1)
16. **저장소**: 데모의 claude.ai 공유 저장소 대신 브라우저 저장(IndexedDB, 사진·영상 파일 포함). 쓸 수 없으면 메모리 저장으로 바꾸고 "새로고침하면 사라져요"라고 알린다. 같은 브라우저의 다른 탭에도 바로 반영(BroadcastChannel). 예시 게시글은 7-1에서는 넣지 않았다가 시연 준비에서 넣었다(23번).
17. **거친 표현 가리기 버그 수정**: 데모는 띄어 쓴 표현("존 나")을 찾고도 가리지 못했다. 찾은 표현이 원문에서 차지한 구간 전체(사이의 공백·숫자 포함)를 ●로 가린다 ("존 나" → "●●●"). 테스트: `domain/community/community.test.ts`, `src/community.test.tsx`
18. **오탐 줄이기**: "시발점"·"시발역"·"시발택시"는 허용 낱말로 두어 차단하지 않는다 (데모는 차단).

## 7. 7단계 계획

데모의 공유 저장소(`window.claude` db·assets·user)는 claude.ai 전용이라 쓸 수 없다. 그래서 둘로 나눈다.

### 7-1. 저장소 인터페이스 + 브라우저 저장 버전 (완료)

> 아래는 착수 전에 세운 계획이다. 실제로 한 일과 달라진 점은 4절 16~22번과 커밋 메시지를 본다.
> 만든 파일: `domain/community/{moderation,posts}.ts`, `data/community/{browser,memory,shared}.ts`, `data/registry.ts`의 `openCommunityRepository`, `ui/community/*`, `ui/shared/SearchBox.tsx`(선수 검색 상자를 공통으로 옮김), `ui/shared/useNow.ts`. 테스트: `domain/community/community.test.ts`, `data/community/community.test.ts`, `src/community.test.tsx`

**목표**: 데모 커뮤니티의 화면과 기능을 브라우저 저장만으로 완성한다. 새로고침해도 글과 사진·영상이 남는다.

배치
- `domain/community/` — 리그·저장소와 무관한 규칙. **서버(7-2)에서도 그대로 쓸 수 있게** 브라우저 API(DOM, `window`, IndexedDB)와 외부 패키지에 의존하지 않는 순수 TypeScript로 둔다.
  - `moderation.ts`: 작성 제한 규칙(심한 욕설·혐오·비하·위협·전화번호는 차단하고 걸린 표현과 이유를 알려 줌, 거친 표현은 ●●로 가림, 띄어쓰기·숫자·기호를 끼운 우회 표현 걸러내기). 표현 목록은 데모 `MOD`에서 옮긴다.
  - `posts.ts`: 게시 검사(본문 또는 파일 필수, 파일 최대 4개·20MB·PNG/JPG/WEBP/GIF/MP4/WEBM), 30초 도배 제한, 본문 속 선수 이름 자동 태그, 신고 3번 누적 시 가리기, 선수별 관련 글 수·최근 24시간 글 수, 이번 주 많이 이야기된 선수
- `data/community/` — 저장소
  - `repository.ts`: `CommunityRepository` 인터페이스 — 글 목록 구독/불러오기, 글 쓰기(미디어 포함), 좋아요 토글, 신고, 삭제, 미디어 주소 얻기, 현재 사용자
  - `browser.ts`: 브라우저 구현. 글과 사진·영상 파일(Blob)을 **IndexedDB**에 저장. 미디어는 Blob URL로 보여 주고 다 쓰면 해제. 사용자는 기기별 로컬 사용자 하나
- `ui/community/` — 커뮤니티 화면(글쓰기·미리보기·선수 태그·작성 제한 안내·필터·피드·좋아요·신고·삭제·가린 글 펼치기·이번 주 많이 이야기된 선수·작성 규칙), 선수 카드 아래 "커뮤니티 이야기"(관련 글 N개, 최근 24시간 M개, 최근 글 2개, 관련 글 모두 보기, 이 선수 글쓰기)
- 저장소는 ui에서 컨텍스트로 주입(리그 데이터 출처와 같은 방식). 테스트에서는 메모리 구현을 넣는다.

데모에서 고칠 것
- **거친 표현 가리기 버그**: 데모는 띄어쓰기를 지운 문장으로 거친 표현을 찾고(`normTxt`), 가릴 때는 원문에서 그대로 찾아 바꾼다(`maskMild`). 그래서 "존 나"처럼 띄어 쓰면 "가려진다"고 안내만 하고 가리지 않은 채 게시된다. 원문 위치에 맞춰 가리도록 고치고 테스트한다.
- 선수 ID는 `리그:번호` 문자열(데모는 숫자)
- 데모의 시드 게시글("데모 게시글")을 둘지는 7-1에서 정한다.

테스트
- 작성 제한 규칙(차단·가림·우회 표현·전화번호·오탐 예시), 게시 검사, 도배 제한, 자동 태그, 신고 가리기, 집계
- 브라우저 저장소: IndexedDB 저장·새로고침 후 복원(테스트용 IndexedDB 구현 패키지 사용 검토), 삭제 시 미디어도 삭제
- 화면: 글쓰기 → 피드 표시, 차단 안내, 신고 3번 → 가림 → 펼치기, 선수 카드 연동

결정 (사용자 확인, 2026-11-08)
- 대체 해시는 만들지 않는다. Web Crypto(`crypto.subtle`)가 없는 접속(https·localhost 아님)에서는 "localhost나 https 주소로 접속해 주세요"만 안내한다. 사용자는 localhost(VS Code 포트 전달)로 접속한다.
- 로그인 전에 쓴 글은 「익명 팬」으로 남긴다(지울 수 없음, 신고 가능). 예전 응원 기록은 집계에 남고, 장바구니는 브라우저에 하나.
- 시연 데이터 초기화는 기본으로 계정을 남기고, 「가입한 계정도 모두 지우기」(기본 꺼짐)를 고르면 계정도 지운다. 데모 계정은 늘 남는다.
- 닉네임은 허용 수준의 거친 표현도 불가. 좋아요·신고도 로그인 필요. 응원 팀 → 테마 짝: 한빛 수달스=남색·금색, 태백 산양스=버건디·회색, 청운 해오라기스=감청·하늘, 금강 반딧불스=빨강·노랑, 남해 돌고래스=파랑·흰색, 북악 부엉이스=주황·검정(공식 스토어 상품 색도 이 테마 색으로).

결정과 구현 메모 (로그인)
- **계정 id와 익명 글**: 계정 id는 `acct:…`, 데모 계정은 `acct:demo`(닉네임 「체험팬」, 비밀번호 해시가 없어 버튼으로만 로그인). 로그인 기능 전에 쓴 글의 작성자 id는 `local:…`이라 「익명 팬」으로 보이고 어느 계정의 글도 아니어서 지울 수 없다.
- **닉네임 저장**: 글·응원 메시지에 `authorName`(쓸 때의 닉네임)을, 판매글은 원래 있던 `sellerName`에 닉네임을 저장한다. 예전 글은 읽을 때 `authorName: null`로 채운다. 닉네임 변경 기능이 없어 저장 시점 이름으로 충분하다.
- **저장소 사용자**: 커뮤니티·응원방·마켓 저장소의 `user`는 로그인 계정 `{ id, name: 닉네임 }`, 로그아웃이면 `null`(읽기만, 쓰기는 "로그인이 필요합니다"). 넣지 않으면(테스트) 예전처럼 익명 사용자를 만든다. 화면 제공자는 계정이 바뀌면 저장소를 다시 열고, 다시 여는 동안에는 "불러오는 중"으로 보여 준다 — 로그인 직후 판매글 쓰기 화면이 예전 로그아웃 상태를 보고 로그인 화면으로 되돌리던 문제를 테스트에서 찾아 고쳤다.
- **장바구니**: 계정과 상관없이 이 브라우저에 하나. 담기는 로그인 없이, 주문하기만 로그인.
- **로그인 필요 안내**: 버튼은 그대로 보이고, 누르면 `/login?next=지금 화면`으로 간다. 돌아갈 주소는 앱 안 경로(`/`로 시작, `//` 아님)만 받는다. 써 두던 글자는 sessionStorage에 잠시 보관했다가 돌아오면 채운다(사진 제외).
- **Web Crypto**: `isSecureContext`가 false이거나 `crypto.subtle`이 없으면 가입·로그인 화면에 "localhost나 https 주소로 접속해 주세요"만 보여 준다(대체 해시 없음, 사용자 결정). 해시는 PBKDF2-SHA256 10만 번, 계정마다 무작위 16바이트 salt.
- **응원 팀 테마**: 가입할 때 한 번 화면 설정의 테마를 바꾼다. 화면 설정은 계정이 아니라 브라우저에 저장되므로, 로그인·로그아웃으로 테마가 바뀌지는 않는다.
- **테스트**: `domain/auth/account.test.ts`, `data/auth/auth.test.ts`, `data/accounts-link.test.ts`(세 저장소의 계정 연결, 예전 글), `src/auth.test.tsx`(화면 흐름). 로그인이 필요해진 기존 시연 흐름 테스트(`demo-community`, `cheer`)는 데모 계정으로 로그인한 상태에서 시작하게 바꿨다.

### 12-2. 배경 진하기 (사용자 요청: 너무 연하다, 2026-11-08)

### 12-3. 버그: 장식을 켜면 팀 색이 사라짐 (2026-11-08, 사용자 제보·다크 모드)

- **원인**: 장식 층은 무늬 모양 마스크라 무늬 밖은 투명했고 바탕 그라데이션도 덮어쓰지 않았다. 문제는 장식을 켤 때 함께 깔리는 **반투명 막**이었다. 막은 내 사진 위 글자를 읽기 쉽게 하려고 만든 것이라 중립 바탕색(`--paper`)을 85%로 덮어서, 팀 색이 15%만 비쳐 기본 색처럼 보였다.
- **수정**: 순서는 그대로(팀 색 → 장식 무늬 → 막). 막은 사진이 없으면 바탕과 같은 팀 색 그라데이션(`--bg-top/--bg-bottom` 85%, `data-over="theme"`), 사진 위에서만 중립 바탕색이다. 그래서 무늬 밖은 팀 색 그대로이고 무늬만 흐리게 비친다(이때 7.5%, 12-4절에서 15%).
- **무늬 색**: 강조색 무늬는 팀 색 배경을 더 진하게 만들어, 무늬 자리까지 대비를 지키려면 배경 비율을 크게 줄여야 했다(「진하게」가 「보통」과 같아지는 테마도 생김). 사용자가 확인한 배경색을 바꾸지 않으려고, 팀 테마에서는 무늬를 중립색(라이트 #FFFFFF, 다크 #121821, `--deco-neutral`)으로 칠해 무늬 자리가 바탕 쪽으로 옅어지게 했다(대비가 늘 같거나 좋아진다). 기본 테마와 사진 위에서는 예전처럼 강조색 무늬.
- **테스트**: `src/background.test.tsx`(11개 테마 × 3단계: 장식을 켜기 전후 팀 색 변수가 같고, 막이 팀 색으로 깔리는지), `domain/theme/surface.test.ts`(`visibleBackground`: 11개 테마 × 3단계 × 라이트·다크에서 무늬 밖 색이 같고, 무늬 자리 글자 대비 4.5:1 이상), `scripts/tokens.test.ts`(막·무늬 CSS 규칙과 값).

### 12-4. 장식 무늬를 더 진하게 (2026-11-08, 사용자 요청)

- 장식 층 불투명도를 50% → 100%(`DECORATION_OPACITY = 1`, settings.css `.app-bg-deco` opacity:1)로 올렸다. 막(85%) 사이로 비치므로 무늬는 약 7.5% → 15%로 보인다.

- **추격타의 점수 차**: 안타로 좁힌 **뒤에 남은** 점수 차(1점 차·2점 차·3점 차 이상). 아직 지고 있는 상태로 득점한 안타만 추격타다(동점이 되면 동점타, 앞서면 역전타).
- **「팀이 이긴 경기만」은 타자의 모든 항목**(역전타·동점타·추격타·도루·호수비)에 적용한다. 투수는 승패와 관계없다.
- **이닝 배수**: 그 일이 일어난 이닝 기준(투수의 리드 지키기는 리드를 안고 등판한 이닝 기준). 1~6회 1배, 7~9회 1.5배, 연장 2배.
- **기대 점수**: 상황 종류(타격 기회·도루 기회·수비 기회·위기 등판·1점 차 리드 등판·2점 차 이상 리드 등판)와 이닝 구간마다 「리그 전체 점수 ÷ 리그 전체 기회」를 구해 이 선수의 기회 수에 곱해 더한다.
- **승리 환산 비율**: 점수표 파일의 고정 상수(가상 리그 기준으로 1위 추가금이 1억~1억 5천만 원이 되게 정하고 테스트로 확인). 리그마다 자동으로 맞추지 않는다 — 점수표처럼 사람이 조정하는 값으로 둔다.
- **반올림**: WAR와 클러치 점수(승)는 0.1 단위로 반올림해 계산한다. 화면의 「WAR 3.2 → 3.2억」과 금액이 늘 맞고, 0.1당 1,000만 원이 정확히 지켜진다.
- **스탯 조절은 그 선수만 바꾼다**: 리그 평균(wOBA, FIP 상수, 리그 ERA 등)은 원래 값으로 두고 그 선수의 지표만 다시 계산한다. 타석(타자)은 그대로 두고 안타·볼넷·삼진을 늘리면 범타 아웃이 그만큼 줄어든다. 안타를 바꾸면 단타가, 홈런을 바꾸면 단타가 바뀐다(안타 수 안에서 홈런 비중이 바뀜).
- **자책점**: 이 앱의 투수 WAR는 FIP 기준이라 자책점은 가치에 영향이 없다. 사용자 결정(2026-11-10)으로 투수 스탯 조절에서 자책점을 빼고 ERA는 표시만 한다(이닝을 바꾸면 같은 자책점으로 다시 계산된 ERA가 보인다).

계획
- **data** (`data/demo/season.ts`): 기준일 `DEMO_BASE_DATE`(2026-11-10)의 기록 = 지금까지의 시즌 기록(골든과 같음). 이 시즌 기록을 144경기일에 나눠 둔다(선수마다 출장일을 고르고, 타석 결과·도루·투구 기록·클러치 기록을 경기에 무작위로 나눔 — 합계는 그대로). 기준일의 144일 밖 날짜는 그 선수의 기준 시즌 경기 중 하나를 날짜와 선수로 정한 난수로 골라 그날 경기로 쓴다. 날짜 D의 기록 = D까지 144일의 합. 그래서 같은 날짜는 늘 같은 기록이고, 하루 변화는 경기 하나가 들어오고 하나가 빠지는 만큼이다. 수비(UZR 구성·DRS 등)·트래킹·추가 진루율은 시즌 값 그대로 둔다(데모 단순화).

- **domain** (`domain/value/ranking.ts`): 순위·동점 규칙·전일 비교·급상승/급하락, 한국 날짜 계산.
- **ui**: `LeagueProvider`가 보는 날짜(기본 오늘, 한국 시간 0시가 지나면 다시 불러옴)와 어제 리그를 함께 준다. `/ranking` 화면, 상단 메뉴 「가치 순위」, 선수 카드 `?tab=value`.

결정 (작업 중 사용자 확인, 2026-11-10)
- **클러치 승리 환산 16점 = 1승**: 기록이 매일 바뀌어 클러치 1위 추가금도 날마다 달라진다. 14점이면 2년치 날짜(730일) 중 1억~1.5억인 날이 37%(0.9~2.7억)라, 고정 비율 16으로 바꿨다 → 69%(0.8~2.3억, 중앙값 1.4억), 기준일 1위 1.1억. 날마다 1위에 맞추는 방식은 쓰지 않는다(내 기록이 그대로면 내 추가금도 그대로).

구현 메모
- **기준 시즌 나누기**(`splitHitter`·`splitPitcher`): 타자는 출장 경기(`clutch.games`, 144 이하)를 고르고 타석을 고르게 나눈 뒤, 타석 결과를 섞어 경기 순서대로 자른다. 도루·도루 실패는 1루 출루가 나온 경기에, 클러치 기회는 타석(도루는 1·2루 출루) 비율로 경기에 넣고 성공은 그 기회 중에서 고른다(성공 ≤ 기회가 경기마다 지켜진다). 투수는 등판일을 고르고 아웃을 등판마다 들쭉날쭉하게(최소 1, 선발 최대 24·불펜 최대 9) 나눈 뒤 탈삼진은 아웃 중에서, 피홈런은 피안타 중에서 고른다. 타자 출장 경기 수는 `round(PA/4.3)`이고 144를 넘지 않게 했다(13절의 `PA/4`는 144를 넘었다).
- **기준 시즌 밖의 날**: 처음에는 그 선수의 기준 시즌 경기 하나를 다시 뽑았는데, 시즌의 운이 두 번 들어가 기준일에서 멀어질수록 클러치 점수 퍼짐(표준편차 7.5 → 10~11)과 WAR 최대(5.8 → 7.4)가 커졌다. 그래서 실력 확률(타석 결과, 도루 시도·성공, 클러치 확률 — 생성기와 같은 함수)로 하루 경기를 시뮬레이션한다. 자책점은 내준 출루·홈런으로 대략 계산한다(ERA 표시용, 리그 ERA 3.7~4.1).

- **저장소**: `LineupRepository`(`mine`·`subscribe`·`save`·`resetDemoData`), 브라우저(IndexedDB `saber-note-lineup`, 계정 id가 열쇠, 다른 탭 반영)·메모리. `LineupProvider`가 계정이 바뀌면 다시 연다. 시연 데이터 초기화(`DemoReset`)에 들어가고, 라인업 화면 아래에도 초기화 버튼이 있다.
- **가상 팬**: 점수 = 0.3 × 기준일 예상 가치(억 원) + 인기(구단 인기 + 선수 인기, 시드로 고정), 가중치 = e^점수, 팬마다 응원 팀 선수 ×2.2. 자리 순서대로 뽑고 같은 팬은 한 선수를 한 자리에만. 가치 비중 0.55에서는 우익수 1위가 78%까지 몰려 0.3으로 낮췄다(가장 몰린 자리도 우익수 59%, 나머지 37% 이하). 300개를 만드는 데 약 15ms이고 기준 리그마다 한 번만 만든다. 테스트: 300개 모두 규칙대로, 같은 결과, 자리마다 1위 60% 미만·3명 이상 픽, 픽률과 예상 가치의 상관 0.4~0.95.
- **픽 순위**: 그 자리에 넣을 수 있는 선수(지금 날짜 리그, 기준일 역할)를 픽 수 순으로 10명까지(적으면 있는 만큼, 0표 포함). 같은 픽 수는 같은 순위(이름순으로 놓음). 픽률 분모는 그 자리를 채운 라인업 수. 내 픽은 저장된 라인업만(고르는 중인 것은 넣지 않음).
- **화면**: 야구장 버튼은 SVG 위의 HTML 버튼(%로 얹음, 최소 56px — 휴대폰 폭 야구장 320px에서 겹치지 않는 좌표, 테스트로 확인). 휴대폰 폭에서는 야구장을 패널 가장자리까지 넓힌다. 빈 자리는 패널색 + 점선, 채운 자리는 본문색 바탕(팀 테마와 상관없이 같은 대비). 잔디·흙·라인 색은 `--grass` 등 토큰(라이트·다크, `scripts/lineup-css.test.ts`). 고르기 창은 휴대폰에서 아래에서 올라오는 시트, Esc로 닫고 닫으면 누른 자리 버튼으로 돌아간다. 포지션 탭 12개는 넓으면 6칸×2줄, 휴대폰 4칸×3줄. 상단 메뉴 7개는 720px 이하에서 한 줄 가로 밀기(지금 메뉴는 `scrollIntoView`로 보이게). 작업 환경에서 실제 배치는 볼 수 없어 사용자 확인이 필요하다.
